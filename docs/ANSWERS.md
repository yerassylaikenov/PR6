# Ответы на контрольные вопросы ПР №6

## 1. Как обеспечиваются автоматический обмен данными, согласованность состояний и целостность информации между модулями?

- **Автоматический обмен.** Оркестратор подписан на событие `PurchaseOrderApproved` модуля Б (опрос 250 мс). Получив его, он **сам читает** `totalPurchaseCost` и `poHash` из контракта Б и регистрирует платёж в модуле А (`registerPayment(paymentId, docHash = poHash, amount = totalPurchaseCost)`), затем вызывает `hub.linkPayment`. После `PaymentStatusChanged` модуля А вызывает `hub.finalize`. Ручного переноса нет: в интерфейсе расчётного центра сумма и хеш только для чтения. Факт: платёж регистрируется через 231 мс после подтверждения (AT-1), в 30 прогонах — в среднем 152 мс на этап передачи.
- **Согласованность.** Единый идентификатор `orderId = keccak256("PO-2026-NNNNNN")`, `paymentId = keccak256(orderId, attempt)`. Источник истины — только блокчейн; перед каждым шагом оркестратор перечитывает on-chain состояние (CP-3), при старте и каждые 15 с выполняет reconciliation (CP-6). Итоговый статус ставит хаб по данным обоих модулей. Факт: 0 расхождений в 30 прогонах и 7 заказах приёмки.
- **Целостность.** Хаб сверяет on-chain `amount == totalPurchaseCost` и `docHash == poHash` (CP-4), иначе `AmountMismatch` / `DocHashMismatch`. Документ PO — канонический JSON, его хеш проверяется `verifyDocument`. Факт: подмена суммы на 1 тиын в AT-5 отклонена.

## 2. Как подтверждается успешное выполнение сквозной операции с использованием блокчейн-реестра?

Каждый шаг — настоящая транзакция в локальной сети Hardhat с txHash и номером блока: `createPO → approvePO → registerPayment → linkPayment → markExecuted → finalize` (6 tx на заказ). Подтверждение — событие `OrderFinalized(orderId, paymentId, Paid)` хаба и согласованные статусы трёх контрактов (PO `Approved`, платёж `Executed`, хаб `Paid`). Цепочку можно восстановить только из блокчейна: `npm run trace -- <номер>` и вкладка «End-to-end status» (таймлайн по событиям, сверка суммы и хеша, `verifyDocument`). Пример — `REPORT_DATA.md`, скриншоты `term_02_demo_e2e_paid.png`, `web_05_auditor_paid_timeline.png`.

## 3. Какие угрозы безопасности выявлены при интеграции и как контролируется их возникновение?

Подмена суммы/хеша оркестратором, повтор сообщения, рассинхронизация модулей, компрометация ключа оркестратора, действия без полномочий, отказ модуля, подмена адреса модуля, DoS спамом заказов, раскрытие коммерческих данных (`docs/THREATS.md`, с привязкой к OWASP SC Top 10 2025). Контроль:
- **превентивный** — `onlyRole` по `msg.sender` (SC01), сверка в хабе (SC04), строгие автоматы статусов и идемпотентность (SC03), immutable-адреса модулей и только `view`-вызовы (SC06), отсутствие циклов и переводов (SC05, SC10);
- **детективный** — мониторинг по `orderId`: R-1 (нарушение доступа), R-2 (эксплуатационный сбой), новое R-3 (межмодульное расхождение);
- **проверочный** — 31 тест (unit, fuzz, инварианты), AT-1…AT-7, OWASP-проверка 10/10, проверка секретов, `npm audit`, CI.

## 4. Какие результаты финальных испытаний подтверждают готовность MVP к эксплуатации в учебной среде и какие ограничения сохраняются?

Подтверждают: AT-1…AT-7 — 7/7 PASS; 30/30 успешных прогонов, 0 расхождений, p50 = 478 мс, p95 = 570 мс; восстановление после паузы банка — 2,3 с, после падения оркестратора — 3,5 с без дублей платежа; все попытки без полномочий откатились без изменения состояния; сработали R-1, R-2 и R-3; 31 тест зелёный; OWASP SC Top 10 — 10/10; CI-local пройден. Решение — «готов к учебной приёмке с условиями».

Ограничения: модуль Б — замещающий контракт до подключения PR5 сокомандника; централизованный ключ оркестратора; демо-ключи Hardhat в браузере; только локальная сеть и один экземпляр оркестратора; Slither — только в CI; уязвимости dev-тулчейна (`npm audit`); после `AmountMismatch` заказ разблокируется только перезапуском оркестратора.
