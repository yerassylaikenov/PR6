## 3. Дизайн интеграции (Задание 1 методички)

### 3.1. Единый прикладной сценарий — «B2B-маркетплейс закупок с банковской оплатой»

Ритейлер (магазин) закупает товары у поставщика. Модуль Б отвечает за **коммерческую часть** (каталог, PurchaseOrder, закупочная стоимость, подтверждение поставщиком), модуль А — за **платёжную часть** между покупателем и продавцом (платёжное поручение банка, исполнение расчётным центром). Без Б банку нечего и не на какую сумму платить; без А заказ не может стать оплаченным. Обе функции необходимы.

| | Содержание |
|---|---|
| **Вход** | Ритейлер выбирает товары поставщика в каталоге и количество |
| **Шаг 1 (Б)** | Ритейлер создаёт PurchaseOrder: позиции, `totalPurchaseCost = Σ qty × unitPurchasePrice`, `poHash` |
| **Шаг 2 (Б)** | Поставщик подтверждает PO |
| **Шаг 3 (авто Б→А)** | Оркестратор ловит событие подтверждения, читает сумму и хеш PO из контракта Б и **сам** регистрирует платёжное поручение в контракте А (`registerPayment(paymentId, docHash = poHash, amount = totalPurchaseCost)`), затем `hub.linkPayment` |
| **Шаг 4 (А)** | Расчётный центр исполняет (или отклоняет) платёж |
| **Шаг 5 (авто А→Hub)** | Оркестратор ловит `PaymentStatusChanged` и вызывает `hub.finalize(orderId)`; хаб **сам перечитывает оба контракта** и ставит итоговый статус |
| **Выход** | Итоговый статус заказа `Paid` (или `PaymentFailed`) + цепочка txHash всех шагов |
| **Результат для пользователя** | Ритейлер видит «оплачено», поставщик — «оплата получена, можно отгружать», аудитор — сквозную историю заказа по одному `orderId` |

Ответственность: ритейлер — состав заказа; поставщик — подтверждение цены и заказа; банк покупателя (оркестратор, OPERATOR_ROLE) — регистрация платежа строго по данным PO; расчётный центр — исполнение; хаб — итоговый статус по данным обоих модулей; администратор — роли и аварийная пауза.

### 3.2. Контракт взаимодействия модулей → `docs/DATA_CONTRACT.md`

- **Общий идентификатор:** бизнес-номер `PO-2026-NNNNNN`; `orderId = keccak256(utf8(номер))` (bytes32). Если в модуле Б poId — `uint256`, хаб хранит соответствие `orderId → poId`.
- **paymentId** = `keccak256(abi.encode(orderId, attempt))`, `attempt` начинается с 1. Уникальность гарантирует мой контракт (`PaymentAlreadyExists`).
- **Документ PO (off-chain, `data/orders/<номер>.json`):** канонический JSON (отсортированные ключи, без пробелов): `{ orderNo, orderId, retailer, supplier, currency: "KZT", items: [{ sku, name, qty, unitPurchasePrice }], totalPurchaseCost, createdAt }`. Суммы — целые числа в тиынах (1 ₸ = 100 тиын). `poHash = keccak256(canonicalJson)`; если модуль Б уже считает хеш по-своему — используем его способ.
- **Сообщение интеграции** (журнал оркестратора и телеметрия): `{ operationId, orderId, step: "REGISTER_PAYMENT"|"LINK"|"FINALIZE", attempt, amount, docHash, sourceTx, resultTx, outcome, ts }`, где `operationId = keccak256(orderId, step, attempt)`.
- **Источник достоверного состояния:** только блокчейн. Статус заказа — в контракте Б, статус платежа — в контракте А, итоговый статус — в хабе. Файлы оркестратора — кеш, их можно удалить, состояние восстановится.
- **Порядок вызовов/событий:** `createPO (Б) → approvePO (Б) → [событие] → registerPayment (А) → linkPayment (Hub) → markExecuted|markRejected (А) → [событие] → finalize (Hub)`.
- **Права доступа:** см. таблицу ролей в §4.4; всё проверяется контрактами по `msg.sender`.
- **Обработка ошибок:** таблица «ошибка → реакция оркестратора»: `EnforcedPause` / RPC timeout → повтор с backoff (1, 2, 4, 8 с, максимум 5 попыток), затем алерт R-2 и ожидание; `PaymentAlreadyExists` → считать шаг уже выполненным (идемпотентность) и перейти к link; `AlreadyLinked` / `AlreadyFinalized` → шаг выполнен; `AmountMismatch` / `DocHashMismatch` → **не повторять**, алерт R-3, компенсация (`cancelPayment` ошибочного платежа); `AccessControlUnauthorizedAccount` → алерт R-1, остановка обработки заказа.

### 3.3. Четыре критерия приёмки → `docs/ACCEPTANCE_CRITERIA.md`

| ID | Критерий | Как проверяется |
|---|---|---|
| **К1** | Нет ручного обмена: после подтверждения PO платёж регистрируется автоматически не позднее 10 с; в банковском интерфейсе нет полей для ручного ввода суммы и хеша заказа | AT-1 + замер времени; ревью UI |
| **К2** | Согласованность состояний: во всех прогонах статусы PO, платежа и хаба согласованы, сумма и хеш совпадают | скрипт сверки `reconcile`: 0 расхождений на 30 прогонах |
| **К3** | Защита общей операции: действия без полномочий, подмена суммы или хеша и повтор сообщения не меняют состояние | AT-2, AT-3, AT-5 + срабатывание R-1/R-3 |
| **К4** | Восстановление после сбоя: после отказа банка (пауза) или падения оркестратора все незавершённые заказы доводятся до согласованного итога без дублей платежа, не позднее 60 с после восстановления | AT-4, AT-6 |

### 4.2. Контракт `OrderSettlementHub.sol` (≈ 100–150 строк, OpenZeppelin AccessControl + Pausable)

```solidity
enum OrderStatus { None, AwaitingPayment, Paid, PaymentFailed }
struct OrderLink { /*poId или bytes32*/ ; bytes32 paymentId; uint32 attempt; bytes32 docHash;
                   uint128 amount; OrderStatus status; uint64 linkedAt; uint64 finalizedAt; }
bytes32 ORCHESTRATOR_ROLE;
constructor(address retail, address bank, address admin)   // адреса модулей immutable

function linkPayment(bytes32 orderId, uint32 attempt) external onlyRole(ORCHESTRATOR_ROLE) whenNotPaused;
//  читает PO из модуля Б: существует, статус «подтверждён»
//  paymentId = keccak256(abi.encode(orderId, attempt)); читает платёж из модуля А: status == Registered
//  CP-4: payment.amount == po.totalPurchaseCost  else AmountMismatch
//        payment.docHash == po.poHash            else DocHashMismatch
//  повтор: если уже AwaitingPayment с тем же attempt → AlreadyLinked
//  новая попытка допускается, только если предыдущий платёж в финальном неуспешном статусе
//  emit OrderPaymentLinked(orderId, paymentId, attempt, amount, docHash)

function finalize(bytes32 orderId) external;   // вызвать может любой: всё проверяется по данным модулей
//  status должен быть AwaitingPayment, иначе AlreadyFinalized / NotLinked
//  payment.status == Executed → Paid; Rejected или Cancelled → PaymentFailed; иначе NotSettledYet
//  emit OrderFinalized(orderId, paymentId, finalStatus)

function getOrder(bytes32 orderId) external view returns (OrderLink memory);
```

Требования: custom errors; `msg.sender`, без `tx.origin`; нет внешних вызовов, кроме `view`-чтения двух модулей (адреса фиксированы в конструкторе); комментарии с отсылками к OWASP SC Top 10 (2025): SC01, SC03, SC04, SC10. Если модулю Б нужен статус «оплачено» (например, отгрузка разрешена только после оплаты) и в контракте Б есть подходящая функция — оркестратор вызывает её автоматически после `Paid`; если нет — итоговый статус живёт в хабе, а UI поставщика читает его оттуда.

### 4.3. Оркестратор (`npm run orchestrator`, Node + viem, API 127.0.0.1:8788)

- Слушает события модулей Б и А (опрос с `pollingInterval` 250 мс), обрабатывает строго по правилам §3.1.
- **CP-3 идемпотентность:** перед каждым шагом читает состояние on-chain (платёж уже есть? заказ уже связан? финализирован?) и пропускает выполненное; хранит обработанные ключи `txHash:logIndex` и `operationId` в `state/outbox.json` (кеш).
- **Повторы:** backoff 1/2/4/8 с, максимум 5 попыток, затем алерт R-2; заказ остаётся `AwaitingPayment` / «ожидает оплаты».
- **CP-6 reconciliation:** при старте и раз в 15 с проходит по всем заказам, подтверждённым в модуле Б, и доводит незавершённые до конца по фактическому состоянию блокчейна. Работает даже после удаления `state/`.
- **API только на чтение:** `GET /health`, `GET /orders`, `GET /orders/:orderNo` (сводка из трёх контрактов + txHash шагов). Слушает только `127.0.0.1`; изменяющих эндпоинтов нет.
- Отправляет телеметрию в монитор (`correlationId = orderId`).
- **Флаги внедрения отказов** — только для приёмочных тестов, в `.env.example` выключены: `FAULT_TAMPER_AMOUNT=1` (регистрирует платёж на сумму +1 тиын — имитация скомпрометированной интеграции), `FAULT_CRASH_AFTER=REGISTER_PAYMENT` (процесс завершается после этого шага).

### 4.5. Единая точка входа — web (`http://localhost:5173`)

Одно приложение, сверху — выбор кошелька и роли; у каждого шага видны стадии транзакции, txHash, блок, gasUsed.

- **Кошелёк:** (1) **«Локальный тестовый аккаунт»** — выбор из списка §4.4, ключ выводится из публичной тестовой мнемоники, режим работает **только при chainId 31337** и `VITE_DEMO_MODE=true` (показать предупреждающую плашку). Это основной режим для защиты — не нужно переключать аккаунты в MetaMask. (2) **MetaMask** (EIP-1193) — как в PR5, с guard сети. Оба режима отправляют настоящие транзакции.
- **Каталог и корзина (ритейлер):** 8–10 синтетических товаров двух поставщиков из `data/catalog.json` (название, SKU, единица, закупочная цена в ₸). Корзина допускает товары одного поставщика; сумма считается автоматически; кнопка «Оформить закупку» создаёт PO в модуле Б.
- **Заказы (поставщик):** входящие PO, кнопка «Подтвердить».
- **Расчёты (клиринговый центр):** платежи в статусе Registered, созданные оркестратором (сумма и хеш **только для чтения**), кнопки «Исполнить» / «Отклонить». Ручного ввода суммы нет.
- **Сквозной статус заказа (аудитор):** по номеру PO — таймлайн всех шагов из трёх контрактов (статус, txHash, блок, время, актор), сверка «сумма PO = сумма платежа», «poHash = docHash», `verifyDocument` по документу; итоговая плашка `Paid` / `PaymentFailed` / `AwaitingPayment`.
- **Мониторинг:** последние алерты R-1/R-2/R-3 и статус оркестратора (`/health`).
- Негативная кнопка «Попытка без полномочий» (например, нарушитель подтверждает чужой PO) — показывает расшифрованную ошибку и неизменное состояние.

Переиспользуй мой dApp из PR5 (машина состояний tx, декодирование ошибок, дедуп событий) и UI сокомандника, где это удобно.

### 4.6. Деплой, данные и запуск одной командой

- `npm run deploy:all` — деплой А, Б, Hub, выдача ролей по §4.4, запись `deployments/localhost.json` и `web/public/deployment.json`.
- `npm run seed` — каталог (без заказов, чтобы демо начиналось с чистого листа) и 1–2 уже завершённых заказа для наглядности истории.
- **`npm run demo:up`** — одна команда: Hardhat node → ожидание порта → deploy:all → seed → orchestrator + monitor + web (через `concurrently` с цветными префиксами). Плюс `launchers/start_all.cmd` для Windows, открывающий отдельные окна (node, orchestrator, monitor, web) с понятными заголовками — как в моём PR5.
- **`npm run demo:e2e`** — сквозной сценарий одной командой без ручных действий: ритейлер создаёт PO → поставщик подтверждает → (оркестратор сам) → клиринг исполняет → (оркестратор сам) → `Paid`. Каждый шаг печатается с txHash и блоком, в конце — сводная таблица состояний трёх контрактов. Лог → `reports/e2e/demo-e2e.log`.
- `npm run trace -- PO-2026-000001` — сквозная история заказа из телеметрии и блокчейна в терминале.
- `npm run demo:reset` — остановка, очистка `state/`, `deployments/`, логов текущего прогона.

## 5. Этап 3 — мониторинг (Задание 3.1)

- Объедини мониторинг обоих PR5 в `monitor/`: один коллектор, единый формат записи `{ ts, correlationId(=orderId), module: "retail"|"bank"|"hub"|"orchestrator"|"web", category, actor, txHash, blockNumber, outcome, errorName, severity }`, файл `reports/monitoring/telemetry.jsonl`. Секреты не логируются.

- **Новое правило R-3 «межмодульное расхождение» (High, CP-5):** (а) платёж `Executed`/`Rejected` в модуле А, а хаб не финализировал заказ дольше 30 с; (б) отказ сверки `AmountMismatch` / `DocHashMismatch`; (в) PO отменён или изменён в модуле Б при живом платеже в модуле А. Антидубль: cooldown 5 мин по ключу `R-3:orderId`. Источники — квитанции, события и журнал оркестратора, а не только `eth_getLogs` (события откатившихся транзакций в журнал не попадают).

## 6. Этап 4 — приёмочные проверки интеграции (Задание 3.2)

`npm run acceptance` — автоматический прогон на поднятом стенде, у каждой проверки: шаги, ожидаемый результат, **фактический** результат (txHash, статусы трёх контрактов до/после, алерты), PASS/FAIL. Результат → `reports/acceptance/AT-*.json` + сводка `reports/acceptance/SUMMARY.md`.

| ID | Проверка | Как воспроизводится | Ожидаемо |
|---|---|---|---|
| AT-1 | Успешный процесс | полный сценарий | `Paid`, сумма и хеш совпадают, все шаги — реальные tx |
| AT-2 | Недопустимые полномочия | нарушитель: подтвердить чужой PO; вызвать `registerPayment`; вызвать `hub.linkPayment`; ритейлер — исполнить платёж | все откатываются, состояние не меняется, R-1 |
| AT-3 | Дублирование сообщения | повторно подать оркестратору то же событие (`replay`) + прямой повторный `linkPayment` | ровно один платёж; `AlreadyLinked`; итог не меняется |
| AT-4 | Отказ одного модуля | админ ставит банк на паузу → поставщик подтверждает PO → оркестратор получает `EnforcedPause`, повторяет, R-2 → `unpause` | заказ автоматически доходит до `Paid`, дублей нет |
| AT-5 | Несоответствие данных | `FAULT_TAMPER_AMOUNT=1` | `linkPayment` откатывается `AmountMismatch`, R-3, заказ не становится `Paid`; компенсация: ошибочный платёж отменён, после выключения флага — попытка 2 с верными данными → `Paid` |
| AT-6 | Восстановление после сбоя | `FAULT_CRASH_AFTER=REGISTER_PAYMENT`, затем клиринг исполняет платёж при «мёртвом» оркестраторе (R-3 через 30 с), затем перезапуск без `state/` | reconciliation доводит заказ до `Paid` ≤ 60 с, дублей нет |
| AT-7 | Отклонение платежа (доп.) | клиринг отклоняет | `PaymentFailed`, статусы согласованы |

## 7. Этап 5 — 30 повторов и финальная приёмка (Задание 3.3–3.4)

**E2E-эксперимент** (`npm run load:e2e`): 30 последовательных повторов полного сценария через живой оркестратор, одинаковые условия (свежий деплой, automine, одинаковый состав заказа, прогрев 2 прогона не учитывается). Клиринговое исполнение в прогоне делает скрипт от имени расчётного центра — это отметить в методике. Метрики: доля успешных операций; число расхождений состояний (сверка после каждого прогона); сквозная задержка от отправки `createPO` до события `OrderFinalized` — **p50, p95** (метод ближайшего ранга), min/max; разбивка задержки по этапам (Б, передача, А, финализация); gasUsed по шагам. Результаты → `reports/load/e2e-raw.csv`, `e2e-metrics.json`, `SUMMARY.md` + SVG-графики (p50/p95, задержка по прогонам, вклад этапов). В анализе — ограничивающий компонент (ожидаемо: интервал опроса оркестратора и последовательность шагов, а не контракты) и одна обоснованная мера оптимизации.

**Финальная приёмка** → `docs/ACCEPTANCE_REPORT.md`: таблица К1–К4 с фактическими доказательствами; результаты AT-1…AT-7; итоги 30 повторов; отсутствие несанкционированных изменений состояния; работа мониторинга (какие правила сработали и где); **выявленные дефекты** (честно, с серьёзностью), **остаточные риски** (централизация ключа оркестратора, демо-режим локальных ключей, только локальная сеть, Slither, если не установлен); **обоснованное решение о готовности** («готов к учебной приёмке / с условиями / не готов»).

**Безопасность:** `docs/THREATS.md` — угрозы именно интеграции (STRIDE, 8–10 строк, с OWASP SC Top 10 (2025)): подмена суммы оркестратором, повтор сообщения, рассинхронизация, компрометация ключа оркестратора, отказ модуля, подмена адреса контракта модуля, DoS через спам заказами, раскрытие коммерческих данных (on-chain только хеши и суммы). Для каждой — мера и проверка (AT/правило).
